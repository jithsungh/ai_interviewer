## 1. Architecture Overview

### High-Level Design

The application is an **AI-powered technical interview platform** organized into 13 domain modules under `app/`. It follows a **layered hexagonal architecture**:

```
API Layer (routes.py)  →  Domain Layer (services.py, entities.py)  →  Persistence Layer (repositories.py, models.py)
     ↕                         ↕                                         ↕
Contracts (DTOs)          Protocols (interfaces)                    ORM Models (SQLAlchemy)
```

### Tech Stack

| Category | Technology | Details |
|---|---|---|
| Web Framework | FastAPI | ASGI, OpenAPI docs, dependency injection |
| ORM | SQLAlchemy | Sync engine, `QueuePool`, declarative Base |
| Primary DB | PostgreSQL | Multi-tenant, BigInteger PKs, JSONB |
| Cache/Locks | Redis | Connection pooling, distributed locks (Lua scripts) |
| Vector DB | Qdrant | Semantic search, cosine similarity, 768-dim default |
| LLM (primary) | Groq | llama-3.3-70b-versatile, httpx async client |
| LLM (stubs) | OpenAI, Anthropic, Gemini | `NotImplementedError` |
| Embeddings | Self-hosted | all-mpnet-base-v2, 768 dims, OpenAI-compatible API |
| Auth | JWT | HS256/RS256, bcrypt password hashing |
| Metrics | Prometheus | Counters, histograms, gauges |
| Sandbox | Docker | Network-isolated, rootless, resource-limited containers |

### Multi-Tenancy

- **`organization_id`** scoping on all admin-owned entities
- **`SUPER_ORG_ID = 1`** for base/global content
- Tenant override tables for all 6 content types (template, rubric, role, topic, question, coding_problem)
- Override merging: `base_content + tenant_overrides → effective_content`

### Entry Point

`main.py` → `app.bootstrap.app.create_app()` → FastAPI instance with middleware, routers, exception handlers, and lifespan management.

1. Creates `FastAPI(lifespan=lifespan, debug=..., docs_url=...)`
2. Registers middleware stack (order matters):

   - `ErrorFormattingMiddleware` (404 reformatter)
   - `CORSMiddleware`
   - `GZipMiddleware`
   - `RateLimitMiddleware` (TODO — placeholder)
   - `IdentityInjectionMiddleware`
3. Registers routers via `router_registry.py`
4. Registers exception handlers

### Lifespan
- **Startup:** PostgreSQL engine+session → Redis → Qdrant (non-critical services warn but don't block)

- `/api/v1/auth` — Auth endpoints
- `/api/v1/admin` — Admin CRUD
- `/api/v1/audio/ingestion` — Audio session control
- `/api/v1/audio/transcription` — Manual transcription

|---|---|---|

| `/logout` | POST 200 | Revoke refresh token (idempotent) |
| `/me` | GET 200 | Current user profile (requires valid access token) |

### Domain Services

#### `AuthService` (1024 lines)
- **register_admin():** Validate password → check email uniqueness → validate org active → hash → create User+Admin → audit log
- **register_candidate():** Validate password → check email uniqueness → hash → create User+Candidate → audit log
- **login():** Find user by email (case-insensitive) → verify password → check user/admin/org status → issue tokens → store refresh hash → update last_login → audit log
- **refresh_token():** Hash incoming token → find in DB → check expiry → **detect token reuse** (revokes all user tokens if detected) → rotate → issue new pair
- **logout():** Hash token → mark as revoked (idempotent)
- **validate_token():** Verify JWT → check user status → check token_version → return claims
- **get_current_user():** Fetch full profile by user_id

#### `JWTService`
- `generate_access_token()`: JWT with claims (sub, type, token_version, iat, exp, jti, admin_id/org_id/role or candidate_id)
- `generate_refresh_token()`: 64-byte cryptographic random, hex-encoded
- `hash_refresh_token()`: SHA-256 for storage
- `verify_access_token()`: Signature + expiry verification

#### `PasswordHasher`
- bcrypt with configurable cost factor (default: 12)
- Complexity validation: min 8 chars, uppercase, lowercase, digit, special character

## 9. Module: `coding`

### Purpose
Sandboxed code execution in Docker containers with test case comparison and scoring.

### Sub-modules

| Layer | Files |
|---|---|
| Root | `__init__.py`, `enums.py` |
| `sandbox/` | `contracts.py`, `docker_runner.py` (363 lines), `executor.py` (394 lines), `output_parser.py`, `sanitizer.py` |

### Enums

| Enum | Values |
|---|---|
| `ExecutionStatus` | pending, running, passed, failed, error, timeout, memory_exceeded |
| `TestCaseStatus` | passed, failed, timeout, memory_exceeded, runtime_error |

### State Machine

```
PENDING → RUNNING → {PASSED | FAILED | ERROR | TIMEOUT | MEMORY_EXCEEDED}
                      (all terminal — no further transitions)
```

### Sandbox (`docker_runner.py`)

**Security hardening:**
- `--network=none` (no network access)
- `--read-only` (read-only root filesystem)
- `--tmpfs /tmp:rw,exec,size=100m` (writable temp)
- `--cap-drop=ALL` (drop all capabilities)
- `--user=1000:1000` (non-root)
- `--security-opt=no-new-privileges`
- `--memory` + `--memory-swap` (equal, no swap)
- `--pids-limit=64` (prevent fork bombs)
- `--rm` (auto-remove)
- Optional seccomp profile

**Language-specific scripts:** Compile (C++/Java with 10s timeout) → Execute with `/usr/bin/time -v` for metrics → Return stdout/stderr/exit_code

### Execution Service (523 lines)

**Workflow:**
1. Acquire lock on submission (prevent concurrent execution)
2. Transition `pending → running`
3. For each test case: execute via sandbox → compare output → classify result → persist
4. Calculate weighted score: `score = (Σ weight × passed) / (Σ weight) × 100`
5. Determine final status from test results
6. Persist final status + score atomically
7. Return structured `ExecutionResult`

**Designed for Celery workers** (synchronous, blocking, not called from FastAPI request cycle).

### Contracts

| DTO | Description |
|---|---|
| `SandboxExecutionRequest` | language, source_code (≤50K chars), input_data (≤10MB), time_limit_ms (100–30K), memory_limit_kb (4MB–1GB) |
| `SandboxExecutionResult` | stdout, stderr, exit_code, runtime_ms, memory_kb, timed_out, memory_exceeded, compilation_output |
| `ExecuteSubmissionCommand` | submission_id, SubmissionData, list[TestCase] |
| `ExecutionResult` | submission_id, execution_status, score, total_time, peak_memory, compiler_output, test_results[] |

### Evaluation

| Function | Description |
|---|---|
| `compare_outputs()` | Normalize (strip trailing whitespace, remove trailing empty lines) → exact match |
| `calculate_score()` | Weighted percentage: `(earned_weight / total_weight) × 100`, rounded to 2 decimals |
| `generate_feedback()` | Status → human-readable string ("Passed", "Wrong Answer", "TLE", "MLE", "Runtime Error") |
| `generate_match_details()` | Visible test cases only — hidden test cases NEVER receive match details |

### Persistence

| Entity / Model | Table | Notes |
|---|---|---|
| `CodeSubmission` | `code_submissions` | FK to interview_exchanges (unique), execution_status, score, time, memory |
| `CodeExecutionResult` | `code_execution_results` | FK to code_submissions + test_cases (unique pair), passed, actual_output, feedback |

## 10. Module: `audio`

### Purpose
Real-time audio ingestion, normalization, buffering, silence detection, and speech-to-text transcription.

### Sub-modules

| Layer | Files |
|---|---|
| `ingestion/` | `service.py` (296), `contracts.py`, `normalizer.py`, `buffer_manager.py`, `silence_detector.py`, `session_manager.py`, `exceptions.py`, `api/routes.py`, `api/contracts.py`, `api/dependencies.py` |

### Audio Ingestion Pipeline

1. **Validate session** (one active session per exchange)
2. **Normalize** (resample to 16 kHz mono, volume normalization)
3. **Buffer** normalized chunks into configurable windows
4. **Feed silence detector** (configurable threshold)
5. **Forward** buffered windows to transcription via callback

**Key contracts:**
- `AudioStreamRequest`: exchange_id, audio_chunk (bytes), sample_rate, channels
- `AudioChunk`: normalized output (16 kHz mono)
- `SilenceDetectedEvent`: exchange_id, silence_duration_ms, should_evaluate
- `SessionAction` enum: START, PAUSE, RESUME, STOP

**API endpoints** (`/api/v1/audio/ingestion`):
- `POST /exchanges/{id}/session/start` — Start audio session
- `POST /exchanges/{id}/session/control` — Pause/resume/stop
- `GET /exchanges/{id}/session/status` — Session status

### Transcription Service

**Provider abstraction** with fallback chain:
- Primary: configurable (whisper, google, local)
- Fallback: ordered chain with per-provider API keys
- Retry: exponential backoff, max 3 attempts
- Timeout: configurable per-call

**Providers:**
| Provider | Status | Streaming |
|---|---|---|
| `WhisperTranscriber` | Implemented (OpenAI API) | No |
| `GoogleSpeechTranscriber` | Implemented | Yes |
| `LocalWhisperTranscriber` | Implemented | No |

**Contracts:**
- `TranscriptionRequest`: audio_data (bytes), sample_rate, language, streaming flag
- `TranscriptionResult` (frozen): transcript, confidence_score [0.0–1.0], segments with timing, provider_metadata
- `TranscriptionConfig`: provider, model, language, word_timestamps, profanity_filter

**Invariants:**
- Audio NEVER written to disk (GDPR)
- API keys NEVER logged
- TranscriptionResult is immutable (frozen dataclass)

## 11. Module: `question`

### Purpose
Semantic question retrieval using Qdrant vector search with fault tolerance.

**Files:** `retrieval/service.py` (430 lines), `retrieval/contracts.py`, `retrieval/domain/similarity.py`, `retrieval/domain/circuit_breaker.py`, `retrieval/persistence/qdrant_repository.py`, `retrieval/persistence/cache_repository.py`, `retrieval/persistence/question_read_repository.py`

### `QdrantRetrievalService`

**Search strategies:**
1. **Semantic search** (`search_semantic()`): Qdrant vector search with embedding similarity
2. **Topic-based** (`search_by_topic()`): Metadata filtering via Qdrant scroll API
3. **Hybrid** (`search_hybrid()`): Weighted combination of resume + JD vectors
4. **Static fallback**: PostgreSQL random selection when Qdrant unavailable

**Fault tolerance:**
- **Circuit breaker** (CLOSED → OPEN → HALF_OPEN): failure_threshold=5, timeout=60s, success_threshold=2
- **Redis caching**: Vector hash → cached `RetrievalResult` (configurable TTL)
- **PostgreSQL fallback**: Degraded path with random question selection

**Similarity/repetition detection:**
- `cosine_similarity()`: Pure math, no I/O
- `IDENTICAL_THRESHOLD = 0.95` (reject same question)
- `SIMILAR_THRESHOLD = 0.85` (reject too-similar)
- `is_acceptable_candidate()`: Below 0.85 similarity to all history

### Contracts

| DTO | Key Fields |
|---|---|
| `SearchCriteria` | organization_id (REQUIRED), query_vector, difficulty, topic_ids, top_k, score_threshold, exclude_question_ids |
| `QuestionCandidate` | question_id, similarity_score, point_id, difficulty, topic_id, metadata |
| `RetrievalResult` | candidates[], strategy_used, total_found, search_duration_ms, cache_hit, fallback_activated |
| `HybridSearchWeights` | resume_weight + jd_weight MUST sum to 1.0 |

## 15. Cross-Cutting Observations

### Architecture Strengths

1. **Clean layered architecture**: API → Domain → Persistence with Protocol-based DI
2. **Comprehensive error hierarchy**: Well-typed exceptions with HTTP status codes, serialization, classification
3. **Multi-tenant isolation**: Consistent `organization_id` enforcement across all modules
4. **Immutability patterns**: Template versioning on mutation, frozen dataclasses for DTOs
5. **Audit trail**: `AuditLogModel` + `AuthAuditLog` for all mutations
6. **Security-hardened sandbox**: Docker with 9+ security flags, no network, rootless
7. **Observability**: Structured JSON logging, Prometheus metrics, distributed tracing, AI telemetry with cost tracking
8. **Fault-tolerant retrieval**: Circuit breaker + Redis cache + PostgreSQL fallback for Qdrant

### Potential Issues

1. **Dual `declarative_base()`**: Auth module uses its own `Base` instead of shared `app.persistence.postgres.base.Base`. This will cause issues with Alembic multi-table migrations.

2. **Auth service uses raw SQL**: `session.execute(text("SELECT ... FROM organizations ..."))` instead of ORM — bypasses any model validation.

3. **No API routes for coding/interview/evaluation/proctoring**: Router registry has these commented out. Only auth, admin, and audio routes are live.

4. **LLM provider stubs**: OpenAI, Anthropic, Gemini providers all raise `NotImplementedError`. Only Groq is functional.

5. **No WebSocket implementation**: `ConnectionRegistry` exists for tracking, but no WebSocket endpoint is implemented. REQUIREMENTS.md describes WebSocket as the transport for interviews.

6. **Missing Alembic migrations**: No `alembic/` directory. Schema is defined in `docs/schema.sql` and ORM models, but no migration tooling.

7. **Sync-only database**: Engine uses sync SQLAlchemy with `QueuePool`. FastAPI's async capabilities are underutilized for DB operations.

8. **RateLimitMiddleware is a TODO**: Placeholder in middleware stack with no implementation.

9. **Audio ingestion uses in-memory buffers**: `_buffers: dict[int, AudioBufferManager]` — not distributed, will lose state on restart, won't work with multiple workers.

10. **Coding module has no API routes**: `ExecutionService` is designed for Celery workers but no Celery configuration exists.
